# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| `plan-fidelity` | Compare **every changed file and substantive hunk** in the diff against the plan's named files or folders, intended behavior, and `## Deviations`; compare additions, omissions, and departures against the PR description and issue. | Each changed file and substantive behavior change must fall within the plan's stated scope or a specific, justified, issue-related deviation documented in the plan and disclosed in the PR description. Every essential planned change must be implemented or replaced by a justified alternative that delivers the same required behavior. Missing essential implementation work, unexplained additions or omissions, unjustified deviations, and contradictions fail this check, even when disclosed. | required |
| `claims-match-diff` | Examine the **title, Summary, Changes, and Notes for Reviewers** against the issue, complete diff, plan/deviations, and observed test results. For **each concrete positive or negative claim**, identify supporting changed lines, absence across the complete diff, or relevant command/output evidence. | The title identifies the actual issue-related change without misrepresenting it, and the description gives a reviewer enough factual context to identify the purpose, substantive changes, and material limits. Every concrete claim agrees with what the diff and results show. A negative claim (e.g., “no new options”) may be proved by the absence of that addition in the complete diff. Unsupported success statements, misleading titles, or descriptions that conceal or contradict material changes fail. Do not demand a particular title style or description length. Interpret each claim in context, including adjacent qualifications and stated conditions. When a shared function changes, distinguish its return behavior from each caller's observable behavior; do not infer a contradiction without supporting diff or execution evidence. | required |
| `behavior-evidence` | Compare the issue's original failing scenario and the plan's test plan with recorded test executions, commands paired with actual output, focused test results, or screenshots demonstrating observed behavior. Cross-check the PR's Testing section against these artifacts. Source code, an unexecuted script, or hypothetical output is not execution evidence. | The PR must provide concrete execution evidence demonstrating that the original failing scenario now produces the issue's expected behavior. Acceptable evidence includes passing tests, executed scripts or commands with actual output, or applicable screenshots or demonstrations. Required verification must be completed and pass. A justified alternative to a planned verification method is acceptable only when it establishes the same corrected behavior and satisfies repository requirements. Missing, hypothetical, or unsuccessful verification does not establish a successful fix. | required |
| `repository-checks` | Compare each applicable required verification command in the repository PR template, `docs/CONTRIBUTING.md`, or an eval package's **repo-facts** block against its recorded command-specific execution evidence (command, relevant output, test-runner summary, or captured exit status) and its reported status in the Testing section. | All applicable tests directly related to the reported issue, its expected behavior, or the behavior modified by the fix must pass. A failure in any directly relevant test fails this check, even when disclosed. Concise, command-specific execution results are sufficient; do not require full terminal logs. A bare claim that tests passed without supporting execution evidence is insufficient. Unrelated test failures do not automatically disqualify the PR.  | required |
| `diff-quality` | Read every changed file and substantive diff hunk alongside the issue and plan boundary; identify unrelated cleanup, debug statements, abandoned or commented-out code, disabled safeguards, or other changes that impede review. | Each hunk has a defensible connection to the issue-related implementation or its focused verification, and the diff contains no unrelated edits or review debris. Disclosure does not make unrelated changes acceptable. Judge relevance and reviewability, not line count, number of commits, or aesthetic preference. | required |
| `standards-comms` | Compare the **title and complete PR description** with the repository's explicit PR-template sections, issue-reference instructions, `docs/CONTRIBUTING.md`, and applicable AI-use policy; in eval mode use only the package's repo-facts and included PR materials. Consider commit metadata only if supplied and an explicit repository requirement makes it relevant. | All **applicable, explicitly required** template sections, issue links, testing reports, AI-use disclosures, and repository policies are satisfied truthfully. A reasoned `N/A` satisfies a conditional section such as screenshots for a backend-only fix. Enforce a commit convention only when the repository states one and the submitted evidence permits checking it. Missing mandatory content or a policy violation fails; do not invent standards from general PR advice. Required information may be conveyed through equivalent prose or sections unless the repository explicitly mandates particular headings, checkbox syntax, or formatting. | required |

## Verdict rule

Verdict rule: Grade each required check pass or fail using the named evidence, recording the deciding fact (specific changed file or hunk, plan or justified deviation, observed verification result, or repository requirement). A check passes only when its requirements are positively established by the available evidence. Missing, insufficient, or contradictory evidence results in fail. Return accept only when every required check passes; otherwise return reject. Preferred checks, if any, provide feedback only and do not affect the verdict.
